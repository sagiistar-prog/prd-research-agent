# 产品决策：让功能回到用户问题

## 为什么需要它

需求讨论往往很快形成文档，却很难追问某个功能为什么属于首版、哪些判断只是猜测、研发如何知道做对了。目标用户是需要把模糊业务诉求带入评审的产品经理，以及随后要理解取舍的研发和测试。

用户的任务不是“生成更长的 PRD”，而是在有限信息下形成可讨论、可拒绝、可验证的交付范围。

## 发现的问题与这次取舍

旧版对汽车配件发货复核需求输出了需求澄清、竞品研究、PRD 生成等模块。这些是工具自己的功能，不是门店的工作。旧版还按列表前后给 Must/Should/Could，并生成固定四周里程碑。

0.3 改成证据整理、语义规划、确定性校验、人工评审四个边界：

- 工具保存原始输入和精确引用，不宣称做了访谈或市场研究。
- 宿主 AI 或人负责识别用户、问题、方案、替代选择和待验证假设。
- 校验器拦住可计算的不一致，包括过期方案、错引、循环依赖、未响应约束和虚构的“输入目标”。
- 评审页把功能、理由、验收和引用放在同一流程里。引用检查通过后仍要求判断它是否真正支持该结论。

没有在这里加入向量数据库：输入是有边界的需求和少量竞品记录，逐条引用已经能解决当前任务。把检索和嵌入强行加入会增加部署成本且不能修复产品判断。大规模资料检索可由上游知识库完成，本工具只接收已选中的证据。

## 两个可复现案例

TeamPulse 从团队反馈到改进行动，先处理小样本隐私和可复盘性，再考虑提醒。FitCheck 从本地工单核对到人工复核，先保证未知和冲突不被隐藏，AI 原因归纳留作后续候选。两例都提供计划 JSON、证据引用、取舍和可测试的行为；它们不是已实现的业务产品。

FitCheck 的原文是一个自然段，技能可以直接读取角色和约束，无需让用户按表单重输。独立试跑发现自然段约束无法进入响应清单，本轮据此修复；同时修正计划生成后摘要仍显示未命名以及重复标点的问题。

## 如何验证价值

当前只有技术和技能试跑证据，没有真实 PM 用户研究。计划让目标用户完成“识别首版范围、定位一个未经证实的判断、找到原文、改写一个不可测试条件”四个任务，记录完成率、耗时和误判，而非统计文档字数。

| 指标 | 口径 | 当前状态 |
|---|---|---|
| 评审任务完成率 | 按预设任务独立完成的任务数 / 总任务数 | 待招募与测量 |
| 追溯耗时 | 从选中功能到找到对应原文的时间 | 无用户基线；自动化只证明路径可走 |
| 无依据判断率 | 人工评审发现既无支持证据又未标假设的判断数 / 所有抽查判断数 | 需人工语义评审 |
| 约束遗漏率 | 未设计响应的真实约束数 / 人工标注约束数 | 代码只保证有标签约束的结构覆盖 |
| 导出一致性 | 导出 Markdown/JSON 与结构化结果是否一致 | 浏览器自动检查 |

不从两个虚构案例推断行业适配率。下一步依据真实评审失败样本改进，优先补充需求变更比较和逐项人工确认，而不是增加自动生成篇幅。
