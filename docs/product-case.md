# 从用户问题到交付

这是产品设计假设与本地实现案例，不是用户研究结论或线上业绩。目标是让评审者可以沿着用户任务、设计取舍、源码和验证记录追问。

## 用户为什么需要它

目标用户：从零散业务想法开始写需求的产品经理。触发时刻：需要把口头想法转化成工程可讨论的范围，却容易漏掉约束与验收。

用户真正要完成的事：形成可被质疑、澄清和验收的需求初稿。价值发生在这个任务完成时，不发生在模型输出字数增加时。

现有替代：通用提示词能写长文，但容易替用户补造背景、竞品事实和功能优先级。差异化假设应通过真实任务对照验证，不能用功能数量或模型名称代替。

## 用户会怎么使用

输入需求与证据 → 检查缺失信息 → 生成需求结构 → 审核假设与范围 → 导出评审稿。

首次使用以示例降低输入成本，再让用户带着自己的合规资料使用。每个处理中状态必须对应真实请求；失败保留输入，结果可复查、可导出。成功不是点击生成，而是用户能做下一步决定。

## 产品定义与技术分工

Skill 引导宿主模型进行需求澄清与结构化；本地CLI提供确定性结构基线。

关键取舍：不把模板当需求洞察；竞品缺点标为输入假设；没有证据的需求留作待确认。最重要的失败模式：固定结构仍不能理解任何新行业的业务实质；需要人和宿主模型澄清。

界面/交互入口：[examples/plugin-input.json](../examples/plugin-input.json)。实现入口：[scripts/plugin_run.py](../scripts/plugin_run.py)。

## 指标定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 任务价值 | 首次评审中无需重写且可直接转为验收讨论的需求项比例；分母为提交首次评审的需求项数 | 自愿参与的任务测试与人工标注 |
| 使用效率 | 从开始有效输入到完成核心动作的中位时长 | 本地计时，不收集原始问题正文 |
| 质量护栏 | 编造竞品事实数、无验收条件项占比、跨行业模板污染率 | 固定回归集和人工抽查 |
| 可用性 | 请求成功率、P95处理延迟、输入恢复成功率 | 去标识事件与运行日志 |

当前没有线上用户基线，不报告增长率或客户收益。先采集基线，再预注册改善目标，避免看完数据再选成功指标。事件字段契约见 metrics.schema.json；它是接入设计，不代表已有生产遥测。

## 价值验证计划

用两个不同行业的虚构需求做盲评，检查功能与原输入一致性、约束保留和验收可执行性；与空白模板相比记录返工。建议首轮覆盖 5 名目标用户用于发现可用性问题，不以该样本估计市场效果。记录任务前提、失败位置和原话；未执行前均为计划。

技术回归与用户验收分开：Schema通过只能证明结构；构建通过只能证明可构建；虚构检索集通过只能证明小样本链路；真实任务成功才支持用户价值。

## 迭代顺序

1. 当前版本：建立明确输入/输出、失败恢复、示例、测试和可审阅文档。
2. 下一版本：增加逐项 evidence_id 和 assumption_id，收集被否决需求的原因后改进澄清流程。
3. 扩展条件：只有核心任务通过且护栏没有恶化，再扩展自动化、数据源或模型。

## 面试时可以展示

先用一个具体任务展示入口与失败状态，再打开设计取舍和测试，解释为什么某些步骤用规则、另一些步骤需要模型。展示本地证据，同时明确线上部署、客户收益和专业有效性未获验证。

外部组件解决通用技术问题；本项目的可归属贡献是问题定义、流程设计、约束、接口集成和验证，不把开源模型能力说成自研算法。
